# 02 · Requirements Document (RD)

**Project:** VittVanni — AI Scheme Analyzer for Marginalized Entrepreneurs
**Version:** v1.0

This document translates the product vision ([`01-PRD.md`](./01-PRD.md)) into
concrete, verifiable requirements. Every requirement carries an ID so it can be
tracked in tests, acceptance, and the roadmap.

## 2. Functional Requirements

### FR-01 · Authentication
| ID      | Requirement                                                            | Priority |
| ------- | ---------------------------------------------------------------------- | -------- |
| FR-01.1 | User can register with a valid email + password (`/api/auth/register`) | Must     |
| FR-01.2 | User can log in and receive a JWT access token (`/api/auth/login`)     | Must     |
| FR-01.3 | Protected endpoints validate `Authorization: Bearer <token>`           | Must     |
| FR-01.4 | User can request a password reset link (`/api/auth/forgot-password`)   | Should   |
| FR-01.5 | User can set a new password via reset token (`/api/auth/reset-password`) | Should |
| FR-01.6 | `GET /api/auth/me` returns the current authenticated user              | Must     |

### FR-02 · Entrepreneur Profile
| ID      | Requirement                                                                | Priority |
| ------- | -------------------------------------------------------------------------- | -------- |
| FR-02.1 | User can create a profile (`POST /api/profile`)                            | Must     |
| FR-02.2 | User can fetch their profile incl. support needs (`GET /api/profile`)      | Must     |
| FR-02.3 | User can update their profile (`PUT /api/profile`)                         | Must     |
| FR-02.4 | Profile includes business, sector, location, enterprise category, social category, funding need |
| FR-02.5 | Questionnaire answers sync into the profile                                | Must     |

### FR-03 · Questionnaire
| ID      | Requirement                                                        | Priority |
| ------- | ------------------------------------------------------------------ | -------- |
| FR-03.1 | 9-question flow renders dynamically from `js/data/questions.js`    | Must     |
| FR-03.2 | Branching questions appear via `showIf` conditions                 | Must     |
| FR-03.3 | Progress bar reflects completion                                   | Should   |
| FR-03.4 | Answers persist per user (synced to profile)                       | Must     |

### FR-04 · Scheme Catalog
| ID      | Requirement                                                                       | Priority |
| ------- | --------------------------------------------------------------------------------- | -------- |
| FR-04.1 | Catalog holds ≥ 70 structured schemes incl. central + state-level coverage        | Must     |
| FR-04.2 | Each scheme exposes the Government Data Structure payload (`GET /api/schemes/{id}`) | Must     |
| FR-04.3 | Scheme list supports filtering (sector, state, type, etc.)                        | Must     |
| FR-04.4 | Scheme seed is versioned and refreshable via `data/schemes_seed_v2.py --force`    | Must     |

### FR-05 · Matching Engine
| ID      | Requirement                                                                        | Priority |
| ------- | ---------------------------------------------------------------------------------- | -------- |
| FR-05.1 | Recommendations apply a **mandatory-rule filter** first (hard eligibility)         | Must     |
| FR-05.2 | Relevance is scored with weighted dimensions (sector > purpose > stage > location > type > size) | Must |
| FR-05.3 | Results are ranked by relevance score and sliced to top-N                          | Must     |
| FR-05.4 | Each result includes a score breakdown and match reasons                           | Must     |
| FR-05.5 | v1 flat and v2 nested response shapes are normalized client-side (`js/matching.js`) | Must     |
| FR-05.6 | Endpoint exposed at both `POST /api/recommendations` and `POST /api/v2/recommendations` | Must |

### FR-06 · Saved Schemes
| ID      | Requirement                                                  | Priority |
| ------- | ------------------------------------------------------------ | -------- |
| FR-06.1 | User can save a scheme (`POST /api/saved-schemes/{id}`)      | Must     |
| FR-06.2 | User can list saved schemes (`GET /api/saved-schemes`)       | Must     |
| FR-06.3 | User can remove a saved scheme (`DELETE /api/saved-schemes/{id}`) | Must |

### FR-07 · i18n & Theming
| ID      | Requirement                                                          | Priority |
| ------- | -------------------------------------------------------------------- | -------- |
| FR-07.1 | UI language toggles between English and Hindi, persisted per user    | Must     |
| FR-07.2 | Strings are tagged with `data-i18n` and resolved via `js/i18n.js`    | Must     |
| FR-07.3 | Dark mode toggle persists and honors OS preference                   | Must     |

### FR-08 · Frontend Pages
| ID      | Requirement                                                                | Priority |
| ------- | -------------------------------------------------------------------------- | -------- |
| FR-08.1 | Pages exist for home, register, login, profile, profile-view, questionnaire, results, scheme-details, saved-schemes, reset-password | Must |
| FR-08.2 | Pages must not call `fetch` directly — only through `js/api.js` wrapper    | Must     |
| FR-08.3 | Frontend runs with zero build step (static host)                           | Must     |

## 3. Non-Functional Requirements

| ID        | Requirement                                                            | Target / Policy                           |
| --------- | ---------------------------------------------------------------------- | ----------------------------------------- |
| NFR-01    | Backend startup & reload under uvicorn                                 | `python run.py` or `uvicorn app.main:app` |
| NFR-02    | API availability                                                       | `/health` endpoint; fast fail on DB error |
| NFR-03    | Performance — recommendations endpoint                                 | p95 ≤ 300 ms on 73 schemes                |
| NFR-04    | Frontend first load                                                     | static only, no build, small JS footprint |
| NFR-05    | CORS allows frontend dev origins                                       | 127.0.0.1:3000/5500/5173, localhost variants |
| NFR-06    | Maintainability — single API wrapper, centralized constants            | `frontend/js/api.js`, `app/utils/constants.py` |
| NFR-07    | Compatibility                                                          | Modern evergreen browsers; mobile-first   |
| NFR-08    | Data integrity before and after destructive scheme re-seed             | users/profiles/saved survived re-seed     |
| NFR-09    | Offline/demo resilience                                                | mock scheme dataset in `js/data/schemes.js` |

## 4. Data Requirements

| ID        | Requirement                                                          |
| --------- | -------------------------------------------------------------------- |
| DATA-01   | Tables: `users`, `entrepreneur_profiles`, `requirements`, `schemes`, `schemes_v2`, `eligibility_rules`, `saved_schemes` |
| DATA-02   | `schemes_v2` is the canonical structured scheme model                |
| DATA-03   | Scheme payload follows the Government Data Structure format (see [`05-api-contract.md`](./05-api-contract.md)) |
| DATA-04   | Eligibility rules stored as `{field, operator, value, required}`     |
| DATA-05   | Every scheme tracks `source_url` and `last_verified` for auditability |
| DATA-06   | Seed scripts idempotent-or-destructive with `--force` flag semantics |

## 6. Security Requirements

| ID      | Requirement                                                             |
| ------- | ----------------------------------------------------------------------- |
| SEC-01  | Passwords hashed with bcrypt via passlib                                 |
| SEC-02  | JWT signed; access token expiry 30 min (configurable)                    |
| SEC-03  | Password reset uses a short-lived `typ=reset` JWT                        |
| SEC-04  | No secrets committed; `.env` gitignored, `.env.example` committed        |
| SEC-05  | Auth dependency wired into all protected routers                         |
| SEC-06  | No logging of passwords or plaintext tokens                              |

## 9. Acceptance Criteria (Top 5)

1. **AC-1:** A newly registered user can complete profile + questionnaire and
   receive **at least one** ranked scheme with a visible score breakdown.
2. **AC-2:** A user who clearly fails a scheme's mandatory rule is not shown that scheme.
3. **AC-3:** Switching EN ⇄ Hindi in the navbar updates UI strings without reload data loss.
4. **AC-4:** Running `python data/schemes_seed_v2.py --force` re-seeds schemes without
   deleting users, profiles, or saved schemes.
5. **AC-5:** `python -m unittest discover tests -v` passes 100% in `backend/tests`.
